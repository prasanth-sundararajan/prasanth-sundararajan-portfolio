No double-bookings: Postgres exclusion constraints, slot holds and webhook-confirmed payments

By Prasanth Sundararajan · 20 November 2026 · 4 min read

A booking system has one job it must never get wrong: two people cannot book the same person at the same time. This is how SlotEase, a FastAPI, React and PostgreSQL booking SaaS, guarantees that while also taking deposits and keeping every open browser up to date.

Why an application check is not enough

The obvious approach is: query for overlapping bookings, and if there are none, insert. Under load that is a race. Two requests run the query at the same moment, both see a free slot, both insert. Locks and serializable transactions can fix it, but the logic is spread across code paths such as booking, rescheduling and late payments, and every new path is a chance to forget.

The more robust answer is to make the database refuse the overlap itself.

An exclusion constraint does the refereeing

PostgreSQL exclusion constraints generalise unique constraints: no two rows may satisfy the given operators at the same time. For bookings, “the same staff member” is = and “overlapping time” is && on a range:

CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings ADD CONSTRAINT ex_bookings_staff_no_overlap
  EXCLUDE USING gist (
    staff_id WITH =,
    tstzrange(start_at, end_at, '[)') WITH &&
  )
  WHERE (status IN ('pending_payment', 'confirmed'));

Three details matter. btree_gist lets a GiST index handle the plain integer equality. The half-open range '[)' means a 10:00–10:30 booking does not collide with one starting at 10:30. And the WHERE clause makes only active bookings occupy time, so cancelled and expired rows stay in the table for history without blocking anyone. In SQLAlchemy it lives in the model's __table_args__:

ExcludeConstraint(
    (column("staff_id"), "="),
    (func.tstzrange(column("start_at"), column("end_at"), literal_column("'[)'")), "&&"),
    name="ex_bookings_staff_no_overlap",
    using="gist",
    where=text("status IN ('pending_payment', 'confirmed')"),
)

Turning the violation into a good response

A violation raises an IntegrityError with SQLSTATE 23P01. SlotEase recognises it by that code or the constraint name, and treats it as “slot taken”. When the customer chose “any staff member”, the service tries each free candidate inside a savepoint, so one collision does not roll back the whole request:

for candidate in free_staff:
    try:
        with db.begin_nested():          # SAVEPOINT
            booking = Booking(staff_id=candidate, status="pending_payment",
                              hold_expires_at=now + timedelta(minutes=10), ...)
            db.add(booking)
            db.flush()                   # the constraint is checked here
        break
    except IntegrityError as exc:
        if not is_overlap_error(exc):    # pgcode 23P01
            raise
else:
    raise ConflictError("This time slot is no longer available")  # HTTP 409

Holds: occupy the slot while the customer pays

Customers pay a deposit, which takes time on a hosted checkout page. The booking is inserted immediately as pending_payment with hold_expires_at ten minutes ahead. Because the constraint covers pending_payment, the hold is enforced by the same rule as a confirmed booking. Nobody else can take the slot while you pay.

A scheduler job runs every minute, marks lapsed holds as expired and fails their pending payments, which frees the slot. The booking path also expires lapsed holds that overlap the requested interval right before inserting, so a customer never waits for the next scheduler tick to get a slot that is really free.

Trust the webhook, not the redirect

After checkout, the customer's browser is sent back to a success URL. That redirect proves nothing: it can be bookmarked, replayed or simply arrive before the payment settles. SlotEase confirms a booking only when Dodo Payments' webhook arrives. The endpoint verifies the Standard Webhooks signature (the webhook-id, webhook-timestamp and webhook-signature headers) and rejects anything that does not match.

Webhooks are delivered at least once, so processing is idempotent. Each event id is stored in a webhook_events table with a unique constraint. A duplicate delivery is acknowledged and ignored, and if processing fails the transaction rolls back, event row included, so the provider's retry gets a clean second attempt.

The late payment edge case

What if the payment succeeds after the hold expired? If the booking is still pending_payment, it still occupies the slot and is simply confirmed. If it already expired, SlotEase tries to flip it back to confirmed inside a savepoint. The exclusion constraint decides: if the slot is still free, the booking is confirmed; if someone else took it, the payment is refunded automatically, and a scheduler retries refunds the provider could not process the first time.

WebSockets: make the UI agree with the database

The constraint guarantees correctness; WebSockets make it pleasant. Each business has a public slot channel. When a booking is held or confirmed the server broadcasts slot.taken, and when a hold expires or a booking is cancelled it broadcasts slot.freed. Every open booking page updates without a refresh, so most customers never see a 409 at all.

The owner dashboard has its own channel with booking events. Browsers cannot set headers on a WebSocket, and tokens in URLs end up in proxy logs, so the client first exchanges its access token for a 60-second, single-use ticket and connects with that.

Events are published only after the database commit, so a browser never hears about a booking that was later rolled back.

Takeaways

  • Put the invariant in the database. An exclusion constraint covers every code path, including the ones you add next year.
  • Model holds as rows covered by the same constraint, with a clear expiry.
  • Only a verified, idempotently processed webhook confirms money.
  • Decide in advance what happens to late payments, and let the constraint decide between confirming and refunding.
  • Push changes to clients after commit, so the UI rarely has to show a conflict.
