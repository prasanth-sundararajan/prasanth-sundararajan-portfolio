How I built a self-correcting data agent with AutoGen

By Prasanth Sundararajan · 20 November 2026 · 4 min read

The hard part of an AI data analyst is not getting the code to run. It is noticing when the code runs fine and the answer is still wrong. These are the design decisions behind DataPilot, a multi-agent AutoGen app that answers business questions about a CSV or Excel file.

The real failure mode is quiet

On clean demo data, a strong model writes correct pandas almost every time. On a real shop export it does not crash; it quietly drops rows. I built a deliberately messy version of the sample sales data to test this: three date formats in one column (2026-08-02, 02/08/2026 day-first, 02-Aug-2026), prices stored as text like ₹1,999, discounts as both 10% and 0.10, and region names spelled South, south and SOUTH.

Before I added any checks, runs on that file were often approved with wrong numbers. In one, 67% of the rows had silently disappeared because of a date parse. A reviewer agent cannot catch that by reading the output, because the output looks perfectly reasonable.

Four roles, one job each

DataPilot splits the work across four AutoGen agents plus the human:

  • Planner sees the question, the column schema and five sample rows, never the full data, and writes a 3–6 step plan.
  • Coder writes one complete pandas and matplotlib script, and rewrites it on an error or on feedback.
  • Executor runs the script in a sandbox, prefixes the result with STATUS: OK or STATUS: ERROR, saves analysis.py and tracks the charts.
  • Reviewer checks every part of the question against the printed numbers and chart labels, then replies FEEDBACK: with concrete fixes, or gives the final answer ending in APPROVED.
  • You, through a UserProxyAgent, approve the answer or ask a follow-up in the same session.

Keeping the full data away from the LLM is deliberate. Every number in the answer comes from code that ran, so it can be reproduced: re-running the saved analysis.py gives exactly the same numbers.

Route with rules, not vibes

AutoGen's SelectorGroupChat can ask an LLM who should speak next. That works, but for this loop the right next speaker is fully determined by the last message, so I use a plain function:

def rules_selector(messages):
    if not messages:
        return "Planner"
    last = messages[-1]
    src, text = last.source, str(last.content)
    if src == "Planner":
        return "Coder"
    if src == "Coder":
        return "Executor"
    if src == "Executor":
        return "Reviewer" if text.startswith("STATUS: OK") else "Coder"
    if src == "Reviewer":
        return "Coder"   # feedback goes back to the code
    return "Planner"     # a new user question

It is cheaper, faster and easier to test than LLM selection. The LLM-based selector and a RoundRobinGroupChat are still available as options in the app, which made it easy to compare them.

Make the sandbox the critic

The fix for quiet failures was to turn them into loud ones. The sandbox gives the Coder a data_check() helper it must call after cleaning. It compares the cleaned frame with a pristine copy of the loaded file and raises a normal Python exception when something looks wrong:

def data_check(raw_rows, df, group_cols=(), date_col=None, max_drop=0.02):
    problems = []
    dropped = raw_rows - len(df)
    if raw_rows and dropped / raw_rows > max_drop:
        problems.append(f"{dropped:,} of {raw_rows:,} rows were dropped")
    for col in group_cols:   # 'North' vs 'north ' counted as two groups
        seen = {}
        for v in df[col].dropna().astype(str).unique():
            seen.setdefault(v.strip().lower(), []).append(v)
        if any(len(v) > 1 for v in seen.values()):
            problems.append(f"column {col!r} has the same value spelled differently")
    if date_col is not None and df[date_col].isna().any():
        problems.append(f"values in {date_col!r} could not be parsed")
    # (the real version also detects day/month swaps against the raw strings)
    if problems:
        raise ValueError("DATA CHECK failed: " + " | ".join(problems))

Because the failure is a real traceback, the existing loop handles it: the Executor reports STATUS: ERROR, the router sends it to the Coder, and the Coder reads a precise message such as “1,496 ISO dates were parsed with day and month swapped” together with a hint (pd.to_datetime(col, format='mixed', dayfirst=True)). The same trick enforces chart quality: a patched savefig fails if a chart has no title, no axis labels or no units.

The sandbox also blocks unsafe calls such as subprocesses, network access and file deletes, and can run inside a Docker container, which is how the public app runs it.

Stop conditions are part of the design

An agent loop without a hard stop is a billing incident waiting to happen. DataPilot's termination is a union of three conditions:

termination = (
    TextMentionTermination("APPROVED", sources=["Reviewer"])
    | FunctionalTermination(reviewer_approved)   # full final-answer format
    | MaxMessageTermination(12)
)

The second condition exists because models sometimes send a complete, correct final answer and forget the magic word. The third guarantees the run ends. On top of that, the public deployment allows only a few live runs per day, counted when a run starts.

What the numbers looked like

With the checks in place, I ran the same hard question on the messy file six times: which region missed its September revenue target by the most, and by how much? It answered correctly six out of six times, and in four of those runs the agents hit at least one real data-check failure and fixed it on their own. Model choice mattered too: a cheaper model for the Coder produced worse results than one strong model for every role, so the defaults use one model with per-agent overrides.

Takeaways

  • Give each agent one job and a strict output format, such as STATUS:, FEEDBACK: or APPROVED, so routing can be plain code.
  • Do not ask a reviewer to spot what it cannot see. Turn domain mistakes into exceptions inside the sandbox.
  • Keep the numbers in code and the language in the LLM, and save the code so every answer is reproducible.
  • Always ship a hard stop and a spend cap.
