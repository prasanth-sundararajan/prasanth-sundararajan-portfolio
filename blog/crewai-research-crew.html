Designing a CrewAI research crew that cites its sources

By Prasanth Sundararajan · 20 November 2026 · 4 min read

LaunchScout takes a business idea, a city and a target customer, and returns a competitor report with prices, customer complaints, the market gap, a recommended positioning and a 30-day launch plan. Every price links to the page it was found on. Here is how the CrewAI crew behind it is put together, and the guardrails that keep it honest.

Why four agents and not one

A single agent with a long prompt can do research, but it blends gathering and judging. It finds two competitors, then starts recommending a strategy based on half the picture. Splitting the job lets each agent be measured against a narrow goal:

  • Market Researcher: find 3–5 real, operating competitors with prices, offers and sales channels, each with a source URL. Tools: web search and a website scraper.
  • Review Analyst: for each competitor, what customers praise and what they complain about, quoting real reviews with sources. Tools: search, scraper and Google Maps reviews, lowest-rated first.
  • Strategy Analyst: a comparison matrix, the single clearest market gap, and a recommended price and positioning. No tools.
  • Report Writer: a founder-friendly six-section report, including the 30-day launch plan, saved as Markdown. Tool: a file writer.

Giving the Strategy Analyst no tools is intentional. It cannot go and find new “facts”; it can only reason from evidence the researchers handed over.

Role, goal and backstory do real work

In CrewAI the backstory is not decoration. It is where you encode the habits you want. The researcher's backstory says it never trusts a number it cannot link to:

researcher = Agent(
    role="Market Researcher",
    goal=(
        "Find 3 to 5 real, currently operating competitors for '{idea}' in {city}, "
        "with their prices, offers and sales channels, each backed by a source URL."
    ),
    backstory=(
        "You spent eight years as a field researcher for a retail consultancy in India. "
        "You never trust a number you cannot link to, and you write down the exact URL "
        "where you saw every price."
    ),
    tools=[search, scrape],
    max_iter=15,
)

All inputs are {placeholders}, so the same crew works for any idea and any city without code changes. Sample runs cover millet meal boxes in Coimbatore and at-home pet grooming in Bengaluru.

Sequential tasks, explicit context

The crew runs with Process.sequential. Each task lists the earlier tasks it depends on as context, so the Strategy Analyst sees both the competitor table and the review analysis, and the writer sees everything:

# abridged
strategy_task = Task(
    description="Compare the competitors and find the clearest market gap ...",
    expected_output="A '## Market Gap' section and a '## Recommended Positioning' section ...",
    agent=strategist,
    context=[research_task, review_task],
)

crew = Crew(
    agents=[researcher, review_analyst, strategist, writer],
    tasks=[research_task, review_task, strategy_task, report_task],
    process=Process.sequential,
)

A hierarchical mode, where a manager LLM plans and delegates, is available as a toggle. For a pipeline with a natural order like this one, sequential was more predictable and easier to debug.

expected_output is a contract

Vague expected outputs produce vague reports. Each task spells out the exact format. The research task, for example, requires a Markdown table with the columns Competitor | Offering | Price | Offers / Subscription | Sales channels | Source URLs, at least three rows, each with a price (or “not listed”) and at least one full https:// URL, plus a list of anything it could not verify. A precise format also makes the output machine-checkable, which the next step relies on.

A guardrail for invented prices

The most damaging failure in research agents is a believable made-up number. CrewAI task guardrails let you inspect an output and send it back with feedback. LaunchScout's price guardrail parses the competitor table and checks every price against the text of the pages and search results the agents actually read during that run:

# simplified from report_utils.price_guardrail
def guardrail(output):
    text = str(output.raw)
    table = competitor_table(text)
    checked = verify_prices(text, evidence)   # evidence = pages read this run
    problems = []
    unbacked = [name for name, r in checked.items() if r["missing"]]
    if unbacked:
        problems.append("These prices do not appear in any page read in this run: "
                        + ", ".join(unbacked) + ". Copy the exact price or replace the competitor.")
    if len(table["complete"]) < 3:
        problems.append("At least 3 competitors need both a found price and a source.")
    return (False, " ".join(problems)) if problems else (True, output)

The feedback is specific enough to act on, so the agent goes back to the competitor's own listing instead of guessing again. After a couple of rejections the output is let through rather than failing the whole crew, and the app's quality checklist flags whatever is left: six sections, at least three competitors, and a price and source on every row.

Tools, fallbacks and cost

Search uses Serper for Google results and Google Maps reviews. Without a Serper key the crew falls back to DuckDuckGo, so it still runs, just with less review data. Because every run spends API credit, the public app counts runs per day under a file lock, so two people pressing Run together cannot both slip past the limit, and failed runs count too.

Showing the work

Multi-agent runs take minutes, and a spinner for that long feels broken. The app shows four status cards, one per agent, plus a live step log of searches and pages read, driven by CrewAI's step callbacks and event bus. Watching the researcher open a competitor's page builds more trust than any disclaimer.

Takeaways

  • Split gathering from judging; give the judge no tools.
  • Write expected_output as a format you can parse and check.
  • Verify numbers against evidence collected in the same run, and send specific feedback when they fail.
  • Design for cost: fallbacks, run limits and visible progress.
